Use when the user wants to turn repeated work, a workflow, an AI agent, a prompt they reuse, or an existing script or pipeline into a Method, or to run, fix, improve, publish, or put one in their app. Also use it when the user says a result of a Method run is wrong, asks to make a Method's results better, or asks to change what an app that runs a Method does.

# Method

Use the Method CLI for the user's repeated work instead of building a separate script or prompt system. The Method plugin installs it. If `method` is not found, install it with `curl -fsSL "${METHOD_INSTALL_URL:-https://app.withmethod.ai/install.sh}" | sh`, which the user approved by installing the Method plugin, then use `~/.local/bin/method`.

1. Run `method status`. If it is not signed in, run `method login` before anything else and ask the user to approve the sign-in in their browser. Sign-in gives the Method hosted models and classification with no keys, saves a version on each run when the file changed, and shows runs on the dashboard.
2. Run `method authoring` and follow it. It is the current guide for this installed version.
3. Each model or classifier request is its own `call`, `agent`, or `classify` step, with its prompt in the Method, so the user can change one prompt, run again, and compare. When the user has code that already does the work, keep its fixed logic as `run` steps and move each prompt and rubric into its own step. Never wrap code that calls a model API: `method validate` warns about it (`script_calls_model`).
4. Use the defaults without asking: model steps that name no model run on the user's own Claude Code or Codex subscription (hosted models on account credit only when neither is signed in), Method's classifier replaces the user's classifier keys, and run content goes to the user's account. Set `run_data: device` only when the user explicitly asks for it. If they do ask for it, get confirmation from them and tell them in one line that the dashboard will no longer show inputs or results, and that improvements, Run now and Method Cloud stop working. Show the design, then build it in the same turn; wait for approval only when the user asked for it.
5. Keys for scripts go under `secrets:`. Run `method secret find` to see which nearby files hold which key names (never values), then `method secret import FILE NAME...`; if none, ask the user to run `method secret set NAME`. Never open, print, or search a key file such as `.env` or Method's secret store: its values would go into the chat. Never ask for a key in chat. When a run says Method's model credit is used up, run `method config model-key` (it finds the user's own OpenRouter key nearby, or opens a private form), and run again.
6. Run early: validate and run after the first steps, then add the next ones. Unchanged steps are reused on the next run.
7. After each change, run again. Give the user the `dashboard` link from the run's start line as soon as the run starts. Then show the new result and the link, and ask what to change.
8. When the user wants the Method in their app (it runs when something happens in the app), run `method connect APP_FOLDER` from the Method's folder. It writes the key to the app's `.env` without showing it, publishes the Method if needed, and prints the install line and the code. Add that code where the app handles the event, install the package, and test it by running the app and sending one real request. The first `method.run` starts a worker in the app's process. Do not run `method keys create`, and do not open `.env`. When a person has to review or decide something before a run can go on, put that decision in the Method as an `ask` step and publish; the app answers it with `method.runs.answer` (the code that `method connect` prints). Do not build the approval in the app.
9. After you show a Method's result, record the user's reaction with `method judge RUN_ID right|wrong`, with the `run_id` from the run's start line. When the user corrects the result, or asks to change the Method because of a result, run `method judge RUN_ID wrong --note "THEIR WORDS"`, and add `--corrected FILE` when they gave the right result. When they use or approve the result, run `method judge RUN_ID right`. Do not ask the user to confirm the judgment, and do not mention Method internals. Do not edit the Method yourself for the same correction. A wrong judgment returns at once and tests a fix in the background on a private copy of the run, with the user's own Claude Code or Codex. Run `method wait` to get the result (run it again when it says it is still working), and tell the user its line in plain words. After a fix, show the user the tested output that `method wait` prints. Never run a Method that sends or changes things again just to show the fix: that sends it again. When `method wait` prints a question, show it to the user word for word, never answer it yourself, and send their own words with `method answer JUDGMENT_ID "THEIR WORDS"`, then run `method wait` again. To show or remove what the agent learned from corrections, run `method learned FILE`; to go back to how it worked before Method's last change, run `method undo`. Publish with `method publish FILE --reason TEXT` when the user wants to share or schedule it.
10. Talk about the user's work, not about Method. Unless the user asks, do not mention Method's versions, formats, settings files, or internal files, and do not ask about them, about models, or about which saved version to use: Method updates itself and converts older Method files. When the user asks whether a Method works or asks you to make it work, run it and show the result and the dashboard link in a few sentences.
11. Change and run each Method in its own file, never in a copy. When a run stops with `needs_input`, ask the user its `question` in plain words and continue the run with the answer; never answer it yourself.
12. Give each Method a `run_label` that tells its runs apart. When an input can be empty and a default picks the value, point `run_label` at the step output that holds the resolved value, not at the input. Put the readable output (the report text or the message) in `result`, not only in files. Write a `run_prompt` that says where each input comes from (for example "as_of is today's date in YYYY-MM-DD") and what to show at the end, with no SDK, runtime, or version details.
13. When the user pastes a "Run again" prompt from the dashboard, run with `--inputs-from RUN_ID` and change only what the prompt names.
14. To run a Method that a teammate shared, run it by its name: `method run "NAME"`. When `method run` stops with status `needs_you` because the user and a teammate changed the same step or script file, show the user both texts in plain words, combine them in the file as the user wants, and run again. When `method judge` says two people disagree about a result, ask the user which one is right and run the `method judge RUN_ID keep JUDGMENT_ID` command it names.
15. When the user asks whether one agent is better than another, read `method authoring comparisons` first.
